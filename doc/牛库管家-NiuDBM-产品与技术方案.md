## 一、总体概述

### 1.1 定位

对标 1Panel 数据库模块，但**只做数据库**，不做面板全家桶。用户装上 fpk 就能建库、建用户、看监控、做备份，不需要懂 Docker、不用敲命令行、不用记端口。

| 维度 | 设计取向 |
| --- | --- |
| 产品定位 | 飞牛 NAS 上的轻量型数据库全生命周期管理器 |
| 目标用户 | 家用 / 小团队 NAS 用户、轻量建站与自建应用开发者 |
| 差异化 | 原生 fpk 一体安装、权限最小化、数据库实例与 NAS 存储卷绑定 |
| 不做的事 | 不做通用容器编排、不做远程多机纳管（P2 再议）、不做 SQL 全功能 IDE |

### 1.2 四条设计原则

1. **最小权限**：应用以专用非特权用户运行，数据库进程同样不越权，绝不碰 `root`。
2. **NAS 友好**：常驻内存尽可能低，数据落在存储卷而非系统分区，能被快照/备份体系覆盖。
3. **引擎与管家解耦**：管家是壳，引擎是插件。换引擎不改 UI，加引擎不改核心。
4. **一切可回滚**：建库、升级、卸载都留退路，删除数据库必须有二次确认 + 回收站期。

### 1.3 核心决策速览

| 决策项 | 结论 |
| --- | --- |
| 应用本体形态 | **原生 fpk（fnpack 普通模板）**，Go 单二进制 + 内嵌静态前端，无外部运行时依赖 |
| 数据库引擎形态 | **内置小引擎 + 按需下载大引擎**，全部原生托管（不依赖 Docker） |
| 容器实例 | **只纳管**：接管已在 NAS 上运行的数据库容器，不代建、不代管（原因见 §2.2） |
| 元数据存储 | 应用私有目录内嵌 SQLite（台账/任务/审计），不额外起数据库 |
| 应用访问模型 | **统一网关（Unix Socket）**：UI 走 `/app/niudbm`，不占用也不暴露宿主 TCP 端口 |
| 用户身份来源 | 网关校验登录态后透传 `X-Trim-Userid` / `X-Trim-Username` / `X-Trim-Isadmin` |
| 数据库实例端口 | 从应用私有端口池分配（TCP），默认仅 `127.0.0.1`，按需对局域网放行 |
| 权限模型 | `run-as=package` 专用用户 + 目录 0700 + 不加入特权组 + 用户级授权目录 |
| 远程访问 | 复用系统访问域名与登录态，不自建穿透、默认不暴露公网 |

## 二、技术栈选型

### 2.1 应用本体运行形态：三个候选

| 候选 | 机制 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 原生 fpk**（普通模板） | 应用文件解包到宿主机，`cmd/main` 直接拉起进程 | 启动快、占用低、可精细控制子进程、调试直观 | 无容器隔离，依赖宿主 glibc、需自管引擎二进制 | ✅ **推荐** |
| B. Docker 模板 | fpk 只声明 `docker-project`，由系统 Docker 托管 compose | 隔离好、引擎版本随便换、依赖打包干净 | 一个包对应一个固定 compose 项目，无法动态派生实例；且与"原生应用"诉求不符 | 不采用（仅纳管场景） |
| C. 纯外部服务 + 轻客户端 | 只装个 Web 壳，连已有数据库 | 包极小 | 与"像装应用一样简单"背道而驰，用户仍需先手动跑容器 | ❌ 不采用为主线 |

**选 A 的理由**：slogan 的承诺是"装应用一样简单"。fnOS 用户最痛的不是"没有数据库"，而是"要先去 Docker 里搜镜像、映射目录、配端口、查权限"。原生 fpk 能把这些全部收敛成一次安装 + 一个向导。

### 2.2 数据库引擎怎么装：本方案最关键的技术判断

必须先说清**一个硬约束**：

> 若应用本体走**原生模板**，进程以 `package` 专用用户运行，**默认不具备操作 Docker 守护进程的权限**（`docker.sock` 属于特权通道）。要通过 API 直接创建/管理容器，只能把应用用户加入 Docker 相关组——**这等价于交出宿主机最高权限**，既违背最小权限原则，也会显著抬高上架审核风险。

因此逻辑上只有两条自洽路线：

- **路线 1（推荐）**：应用原生 + **引擎也原生托管** → 权限边界干净，全程非特权。
- **路线 2**：应用走 **Docker 模板** + 引擎容器化 → 隔离最好，但"原生应用"的诉求落空，且每实例一个容器。
- **不推荐路线 3**：原生应用强行加组去操控 Docker → 权限模型破防。

补充一个容易被误判的点：**Docker 模板并不需要应用自己去拿 Docker 权限**——`docker-project` 声明的 compose 项目由系统托管启停，`cmd/main` 的 start/stop 无需操作容器。真正限制路线 2 的是：一个应用包对应一个固定的 compose 项目，**无法在运行期按用户点击动态派生任意新容器**。而路线 1 若要动态建容器，就必须走路线 3 的特权路径。所以"原生 + 原生托管引擎"不是保守选择，而是唯一同时满足**最小权限**与**动态建库**的组合。

**引擎二进制从哪来，三种取值方式对比：**

| 方式 | 包体积 | 首次可用性 | 架构适配 | 风险 |
| --- | --- | --- | --- | --- |
| 随 fpk 内嵌全部引擎 | 极大（x86+arm 双架构，数百 MB～1 GB） | 装完即用 | 需分别构建 | 包体不可控、更新引擎必须升整个 App |
| **首次创建实例时按需下载**（推荐） | 包体小（仅核心 + 小引擎） | 需一次联网下载 | 按当前架构精准下载 | 需可配置镜像源、必须校验哈希与签名 |
| 依赖系统已有应用/实例 | 最小 | 依赖前置条件 | 天然匹配 | 无法覆盖全部引擎与版本 |

**引擎形态矩阵（最终结论）：**

| 引擎 | 默认形态 | 理由 |
| --- | --- | --- |
| SQLite | 内置（编译进主程序） | 零守护进程，天然契合 NAS |
| Valkey | 内置（单二进制） | Redis 的 BSD-3 分支，规避 7.4+ 许可变更 |
| MariaDB / MySQL | 按需下载（P0） | 体积 60–90 MB，不宜随包内置；二者互斥安装 |
| PostgreSQL | 按需下载（P1） | 官方无通用 Linux 二进制，需自建产物 |
| MongoDB | 只纳管（P2） | SSPL 许可 + 体积大，不自建分发 |

> 分发形态规则、体积账、许可边界、多版本共存与校验链的完整设计见 [引擎分发与版本策略](./引擎分发与版本策略.md)。

**平台能力边界（决定了什么必须自带、什么可以复用）：**

| 平台现状 | 对牛库管家的影响 |
| --- | --- |
| 系统以 `install_dep_apps` 提供 redis / minio / rabbitmq 等中间件 | 外部备份目标可直接复用系统 MinIO；作业轻量缓存可复用系统 Redis，**不必自建** |
| 系统未提供 MySQL / PostgreSQL / MongoDB 类中间件 | 关系型与文档型引擎**必须自行分发**（随包或按需下载） |
| 第三方应用无法被其它应用 `install_dep_apps` 依赖 | 其它 fnOS 应用暂时无法"一键申请"牛库管家内的库，属平台能力缺口，需向平台申请开放 |
| 依赖检查不递归、按从右到左安装 | `install_dep_apps` 只声明**直接依赖**，不依赖嵌套解析 |

### 2.3 技术栈选型

| 层 | 首选 | 备选 | 取舍说明 |
| --- | --- | --- | --- |
| 后端语言 | **Go**（单静态二进制、交叉编译友好、内存占用低） | Rust（更省内存但生态/交付成本高）、Node/Java（运行时重，排除） | NAS 设备多为低功耗 x86/ARM，Go 的常驻开销与交叉编译是决定性优势 |
| HTTP 框架 | 标准库 + 轻量路由 | Fiber/Gin | 待 POC 压测，不预设 |
| 前端 | React/Vue + TypeScript，构建为纯静态资源内嵌进二进制 | 服务端渲染模板 | 需要 iframe 内嵌体验与主题联动，SPA 更合适 |
| 接入层 | **系统统一网关**（Unix Socket，系统校验登录态并透传身份 Header） | 独立 TCP 端口 | 免自建登录、不占端口、天然同域；代价是需适配网关路由与 Header |
| 数据库驱动 | 各引擎**官方协议驱动**（SQL 走标准协议，Valkey/Mongo 走官方驱动库） | 统一走 CLI 工具 | 协议直连可获取结构化错误与指标；CLI 仅作备份/恢复补充 |
| 内嵌元数据 | **SQLite**（WAL 模式） | 无 | 单文件、零运维、可随应用备份 |
| 任务调度 | **进程内调度器 + SQLite 持久化任务表**（支持重试、幂等、并发限流） | 系统 cron、独立队列服务 | 避免引入 MQ；NAS 场景任务量级远未到需要外部组件的程度 |
| 指标采集 | 引擎自身状态接口 + 轻量采样器（默认 60s，可调） | 拉取 Prometheus | 不引入重量级监控栈，采样结果落 SQLite 做趋势 |
| 日志 | 结构化写入应用私有 `var/log`，按大小滚动 | syslog | 需在 UI 内可检索 |
| 打包 | **fnpack**（普通模板，双架构分别构建） | — | 与平台生命周期脚本天然对齐 |

### 2.4 资源占用预算（估算，需实测校准）

| 项 | 空闲 | 备注 |
| --- | --- | --- |
| 牛库管家本体 | 约 40–80 MB 内存 | 单二进制 + SQLite |
| SQLite 实例 | ≈ 0 | 进程内 |
| Valkey 实例 | 约 5–15 MB | 按实例计；默认开启内存上限 |
| MariaDB 实例 | 约 80–200 MB | 取决于缓冲池配置，UI 提供"低配/标准"档 |
| PostgreSQL 实例 | 约 50–120 MB | 同上 |
| 磁盘（引擎解包） | 单引擎约 60–400 MB | 按需下载，不预置 |
| 磁盘（数据） | 由用户卷决定 | 默认落存储卷，不占系统分区 |

**关键取舍**：宁可牺牲"零下载"，也不把 1 GB 的引擎塞进安装包——NAS 用户的系统分区往往只有 64 GB。

## 四、系统架构

### 4.1 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  fnOS 应用中心 / 桌面入口（iframe）                        │
└───────────────┬──────────────────────────────────────────┘
                │ 统一网关 /app/niudbm  →  Unix Socket app.sock
                │ 系统校验登录态，透传用户身份 Header
┌───────────────▼──────────────────────────────────────────┐
│  接入层：网关身份解析 · 应用内角色校验 · 限流 · 审计切面    │
├──────────────────────────────────────────────────────────┤
│  业务层                                                    │
│  实例管理 │ 建库与Schema │ 账号权限 │ 备份恢复 │ 导入导出    │
│  监控采集 │ 日志检索     │ 告警     │ 系统设置 │ 引擎商店    │
├──────────────────────────────────────────────────────────┤
│  能力层                                                    │
│  任务调度器（持久化/重试/幂等） · 凭据保险箱 · 事件总线      │
│  存储适配（本地卷/授权目录/SMB/WebDAV/S3） · 通知通道        │
├──────────────────────────────────────────────────────────┤
│  引擎抽象层 Engine Driver（统一接口，屏蔽引擎差异）          │
│  SQLite │ Valkey │ MariaDB/MySQL │ PostgreSQL │ MongoDB     │
├──────────────────────────────────────────────────────────┤
│  运行时层：原生引擎进程托管（内置/按需包）｜纳管实例仅建立连接  │
├──────────────────────────────────────────────────────────┤
│  平台层：fnOS 生命周期脚本 · 权限声明 · 目录软链 · 开放 API  │
└──────────────────────────────────────────────────────────┘
```

### 4.2 模块划分

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| `gateway` 接入 | 会话、角色、CSRF、限流、审计埋点 | 无状态，所有写操作留痕 |
| `instance` 实例 | 生命周期、端口池分配、目录布局、资源档位 | 端口冲突三重校验（台账/系统/系统调用） |
| `catalog` 建库 | 库/Schema/表元信息、字符集模板 | 屏蔽引擎差异 |
| `iam` 账号权限 | 账号、授权矩阵、白名单、密码策略 | 权限语法由 Driver 翻译 |
| `backup` 备份 | 策略调度、执行、校验、清理、外部上传 | 幂等、可断点、失败必告警 |
| `transfer` 导入导出 | 文件选择（授权目录）、分片、进度 | 大文件不占内存，流式处理 |
| `observe` 监控日志 | 采样、聚合、日志索引、告警 | 采样自身开销 < 引擎开销 1% |
| `engine-driver` 驱动 | 连接、健康检查、dump/restore、指标、用户 SQL | 每个能力标注"支持/降级/不支持" |
| `job` 调度 | 任务表、并发闸门、退避重试 | 同一实例的破坏性任务串行 |
| `store` 元数据 | SQLite 台账、迁移脚本 | 每次启动做 schema 版本校验 |
| `platform` 平台适配 | 目录软链、权限检查、开放 API、通知 | 平台字段变更只影响此模块 |

### 4.3 关键数据流

**① 创建实例并建库**

UI 向导 → 接入层鉴权 → 实例模块做**四重预检**（端口占用、目录可写、磁盘余量、架构匹配）→ 若无引擎二进制则进入"引擎商店"下载校验 → 写入任务表 → 调度器串行执行 → 引擎初始化（生成 root 凭据并加密入保险箱）→ 建库建号 → 记录审计 → 返回连接信息卡片（含复制按钮）。

**② 定时备份**

调度器触发 → 取策略与保留规则 → 生成保护性快照位点（或加锁一致性导出）→ 流式 dump → 压缩（可选加密）→ 落地（默认私有目录 / 用户授权目录）→ 记录校验和 → 按 GFS 清理旧份 → 失败则走告警通道并保留现场。

**③ 外部访问（管理面与数据面分离）**

- **管理面**：始终走统一网关，页面在 `/app/niudbm` 下同域加载，不占用宿主端口。系统校验 NAS 登录态后把用户身份透传给应用，应用据此决定能看哪些实例、能否执行高风险操作（如删库、开外网）。
- **数据面**：用户显式开启"局域网访问"后，引擎仅对指定网段监听并返回连接信息与端口；远程连接依赖系统统一入口，应用侧不引入任何自建隧道，不默认暴露公网。
- 两条链路互不复用，管理面永远不因为数据面开放而暴露在公网上。

**④ 用户在应用内选文件（导入）**

前端 JS SDK 唤起系统文件授权 → 用户选择目录/文件 → 后端通过开放 API 查询授权结果并校验权限 → 转换为可访问路径 → 流式读取。**应用不会因此获得全盘访问能力。**

### 4.4 元数据模型（SQLite 主要表）

`instances`（实例台账与状态）、`instance_members`（NAS 用户可见性授权）、`databases`（库清单）、`accounts`（账号与凭据引用）、`grants`（授权矩阵）、`backup_policies`、`backup_records`、`engine_bundles`（已装引擎包）、`jobs`（任务与重试）、`metrics_samples`（采样时序）、`audit_logs`、`secrets`（凭据密文）、`settings`、`schema_migrations`。

字段级定义、状态机、错误码分段与接口契约见 [数据模型与接口契约](./数据模型与接口契约.md)。

### 4.5 引擎抽象层能力矩阵

| 能力 | SQLite | Valkey | MariaDB/MySQL | PostgreSQL | MongoDB |
| --- | --- | --- | --- | --- | --- |
| 实例生命周期 | 进程内 | ✅ | ✅ | ✅ | 纳管 |
| 逻辑备份 | 文件级 | RDB/AOF | dump | dump | dump |
| 一致性快照 | ✅ | ✅ | 需锁/事务 | ✅ | 需副本集 |
| 用户模型 | 无 | ACL 用户 | `user@host` | role/database | 库级用户 |
| 授权粒度 | 文件权限 | key 模式 | 库/表 | schema/表 | 库/集合 |
| 指标丰富度 | 低 | 中 | 高 | 高 | 中 |
| 典型差异点 | 无网络层 | 无库概念，需逻辑分组 | 需处理 `@host` 与字符集 | 需处理 role 与 search_path | 用户绑定库，无跨库查询 |

### 5.2 生命周期脚本职责映射

| 脚本 | 牛库管家的实际动作 |
| --- | --- |
| `install_init` | 校验存储余量、架构、系统版本；探测端口可用性；拒绝不安全路径 |
| `install_callback` | 初始化私有目录与 SQLite 台账、生成管理员初始凭据、注册开机服务 |
| `main`（start/stop/status） | start 时拉起主进程并监听 `${TRIM_APPDEST}/app.sock`、写 PID，由主进程按台账顺序拉起各引擎实例；stop 时**先优雅停引擎再停管家**并清理 Socket；status 按 exit 0/3 返回 |
| `upgrade_init` | 自动备份元数据库与实例清单，记录版本号 |
| `upgrade_callback` | 执行 schema 迁移，失败则回滚到升级前备份并恢复旧二进制 |

| `uninstall_callback` | 按选择保留或清理私有目录，清理临时与缓存，保留用户显式保留的备份 |
| `config_init` / `config_callback` | 处理授权目录、端口、外部备份目标等配置变更，变更后热重载并校验 |

### 5.3 权限与安全设计（重点）

**① 访问模型与身份来源**

- 管理界面通过**统一网关**提供：应用只监听 `${TRIM_APPDEST}/app.sock`，入口声明 `gatewayPrefix=/app/niudbm` + `gatewaySocket=app.sock`，不声明 `service_port`，**不占用任何宿主 TCP 端口**。
- 系统在转发前完成登录态校验，并注入可信身份 Header：`X-Trim-Userid`、`X-Trim-Username`、`X-Trim-Isadmin`。应用**不实现自有登录体系**，也不信任前端传入的用户标识。
- 应用仍需做业务鉴权：管理类操作（删库、开外网、改授权）要求 `X-Trim-Isadmin=true`；数据展示按 uid 过滤。
- WebSocket 实时监控复用同一网关前缀与 Socket（如 `/app/niudbm/ws`），连接建立时绑定 uid。

**② 运行身份（`config/privilege`）**

- `run-as = package`：使用应用专用用户运行，`username`/`groupname` 取 `niudbm`。
- **明确不使用 `root`**；数据库引擎子进程同样继承该身份。
- **不配置 `join-groups`**。平台虽允许加入附加组以访问特定资源，但本项目所需能力均可在包用户内完成，多一个组就多一份暴露面。
- 若确需特权准备动作，只允许出现在生命周期脚本的极短窗口内，并在启动常驻服务前降权。

**③ 目录与文件权限**

| 目录 | 用途 | 权限 |
| --- | --- | --- |
| `var/`（`TRIM_PKGVAR`） | 引擎数据、SQLite 台账、日志、PID | 0700，`umask 077` |
| `etc/`（`TRIM_PKGETC`） | 配置与凭据密文 | 0600 |
| `tmp/`（`TRIM_PKGTMP`） | 导入导出中转 | 0700，启动时清理残留 |
| `shares/`（`data-share`） | 用户可见的备份包、导出文件 | 系统按 Windows ACL 自动授予应用用户 |
| 用户授权目录 | 导入源 / 备份目的地 | 仅按需申请，**不全盘索权** |

**边界约定**：引擎数据是应用的"私产"，放 `var` 且不对用户暴露为共享目录；用户需要拿走的东西（备份包、CSV 导出）放 `data-share`，在文件管理器里可见可拷。二者不混放，避免用户误删引擎文件或应用越权访问用户文件。

**④ 端口与网络**

- 管理面不占端口（见 ①），这是本方案与多数第三方应用最大的安全差异。
- 数据库实例端口从私有端口池分配（示例 33000–33999），分配前做"台账 + 系统套接字 + 试绑定"三重确认。
- **默认仅监听 `127.0.0.1`**；开启局域网访问是独立开关，需管理员身份 + 二次确认 + 网段限定。
- 公网暴露不做默认能力；远程访问复用系统访问域名与登录态，不自建穿透服务。

**⑤ 文件访问授权与 API Scope**

需要的 Scope 在 `config/resource` 的 `api-scope` 中声明，**只声明实际用到的**：

| Scope | 用途 | 是否声明 |
| --- | --- | --- |
| `trim.file.userAccess` | 当前用户选择导入文件 / 备份目录 | 是 |
| `trim.file.userAcl` | 返回文件或执行导入前校验当前用户权限 | 是 |
| `trim.file.path` | 把 `/vol1/...` 转成用户可读路径展示 | 是 |
| `trim.file.sharedAccess` | 管理员为全体成员统一指定备份目录 | P1 再评估 |
| `trim.system.getPlatformConfig` | 读取系统语言与版本 | 是 |

配套约束：

- 前端调用 JS SDK 前，`manifest` 必须声明 `micro_app=true`，否则页面不会按微应用环境加载。
- 后端 API 只能从应用服务端经系统 Unix Socket 调用，token 来自环境变量 `TRIM_API_TOKEN`，**每次现读，不落盘、不进前端**。
- 拿到授权路径不等于越权通行证：返回内容前仍要用 `trim.file.userAcl` 按当前用户判定。
- 统一网关同域特性可让授权回调页与主页面同源，避免跨域 postMessage 校验问题。

**⑥ 应用内角色模型**

- 角色：**管理员 / 运维 / 只读**，由网关 Header 的 `X-Trim-Isadmin` 与实例归属共同决定。
- 管理员：全实例、开外网、改授权、删库；运维：建库、备份、恢复、启停；只读：看监控与连接信息（密码掩码）。
- 所有写操作与导出行为写入 `audit_logs`，保留周期可配。

### 5.4 manifest 关键声明意图

| 字段 | 意图 |
| --- | --- |
| `appname` / `display_name` | `niudbm` / 牛库管家 |
| `platform` | 分别构建 `x86` 与 `arm` 包（含架构相关二进制时不声明 `all`） |
| `source` | `thirdparty` |
| `os_min_version` | 不低于统一网关所需的最低版本（官方案例标注 1.1.3100），按实测填写 |
| `install_type` | 留空，让用户选择安装位置（系统分区容量有限） |
| `service_port` / `checkport` | **不声明**：纯网关接入，不占宿主端口 |
| `micro_app` | `true`，否则前端 JS SDK 与文件选择能力无法初始化 |
| `disable_authorization_path` | **保持可配置**（需要用户授权导入/备份目录） |
| `install_dep_apps` | 仅声明真实直接依赖，如 `minio`（备份目标）、`redis`（轻量缓存）；不存在数据库类依赖可声明 |
| `ctl_stop` | 保持可启动/停止（用户需要手动停服维护） |
| `desktop_uidir` / `desktop_applaunchname` | 指向 `niudbm.main`，图标按 64/256 双尺寸 + 圆角风格 |

### 5.5 应用中心集成点

1. **入口**：注册一个主入口 `niudbm.main`，`type=iframe`，`gatewayPrefix=/app/niudbm`、`gatewaySocket=app.sock`，`protocol`/`port` 留空不参与路由；`allUsers` 按产品策略决定（建议 `true`，未授权用户进去只能看到空实例列表）。
2. **安装向导**：分步收集"安装位置 → 数据根目录 → 实例端口池范围 → 是否开启局域网访问 → 是否启用离线引擎包"。向导字段自动成为环境变量（自定义字段不使用 `TRIM_` 前缀）。
3. **配置向导**：运行期修改授权目录、外部备份目标、通知通道。
4. **更新与回滚**：`changelog` 面向用户写人话（"新增 PostgreSQL 支持""备份支持 S3"），升级走 `upgrade_init` 备份 + `upgrade_callback` 迁移。
5. **纳管已有实例**：用户填写连接信息即可将 NAS 上已运行的实例纳入统一管理（账号、备份、监控），不重复部署引擎；发现与识别能力放到 P1。
6. **系统能力复用**：打开文件管理器选目录、打开应用设置、读取语言与主题（跟随系统深浅色），全部走开放 API，不自造一套。

## 六、风险与优化

### 6.1 风险清单与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **原生引擎依赖宿主 glibc/CPU 指令集** | 个别设备引擎起不来 | 每个引擎版本建立"已验证机型矩阵"；提供启动前兼容性自检与明确错误提示；优先选静态链接或自包含发行版 |
| **双架构包体膨胀** | 安装包过大、升级慢 | 引擎按需下载 + 主程序按架构拆包 + 灰度镜像源 |
| **引擎下载源不可达** | 首次建库失败 | 支持自定义镜像源与离线导入本地引擎包；UI 明确标识"离线可用"状态 |
| **多实例争抢资源拖垮 NAS** | 整机卡顿 | 实例数上限 + 资源档位 + 连接数上限 + 磁盘水位保护（低于阈值禁止新建） |
| **端口冲突与误暴露** | 启动失败 / 安全事件 | 动态端口池 + 三重探测 + 默认仅本机监听 + 开启局域网需二次确认 |
| **凭据泄露** | 数据泄露 | 保险箱加密、UI 掩码、复制操作审计、强制强密码与定期轮换提示 |
| **引擎许可合规** | 分发受阻 / 法律风险 | 统一"关于"页展示引擎名、版本、许可证与源码出处；GPL 引擎附许可文本；键值引擎改用 BSD-3 的 Valkey；MongoDB 只纳管不代分发 |
| **卸载误删数据** | 不可逆损失 | 双重确认 + 确认词输入 + 默认保留数据 + 删除前强制生成一份备份 |
| **纳管实例的凭据与误操作** | 误删他人库 / 凭据泄露 | 纳管实例标记"外部"并禁止部分高危操作；默认只读接入，写操作需显式开启；凭据入保险箱并审计 |
| **平台字段/API 迭代** | 升级后行为变更 | 平台适配层单独收口，字段变更只改一处；建立版本适配矩阵 |
| **上架审核（权限与安全）** | 分发受阻 | 全程非特权、目录最小化、无隐藏后门与远程控制通道、隐私声明清晰 |

### 6.2 性能与体验优化

- **冷启动优化**：管家主进程先起（< 2 s），引擎实例按"上次活跃"顺序异步拉起并显示逐项进度，避免用户面对白屏。
- **大文件导入导出**：全程流式 + 分片 + 断点续传，禁止一次性读入内存。
- **备份去重**：同库连续备份做增量判断（校验和/位点），减少 NAS 磁盘写放大。
- **日志治理**：滚动 + 分级采样，避免日志把系统分区写满。
- **前端体感**：状态卡片优先渲染骨架屏，长任务全部异步并给"离开页面继续执行"提示。

### 6.3 演进路线

| 阶段 | 目标 |
| --- | --- |
| **M1 可用** | 原生本体 + SQLite/Valkey 内置 + MariaDB 按需；建库、账号、手动备份、恢复、日志、向导安装、卸载保护 |
| **M2 好用** | PostgreSQL、定时备份与外部备份目标、导入导出、监控大盘与告警、角色与审计 |
| **M3 完整** | MongoDB（纳管优先）、引擎商店与多版本共存、结构对比、资源上限、巡检报告 |
| **M4 生态** | 多机纳管（只读聚合视图）、团队协作与配额、向平台申请开放"第三方应用可被依赖"能力后供其它 fnOS 应用申请数据库 |

## 附录 C：一句话收口

牛库管家用**原生 fpk 应用 + 原生引擎托管**换取"装完就能用"和"权限不越界"；把 Docker 作为可选后端而非前提条件——因为一旦为了管容器去获取宿主机特权，"像装应用一样简单"就变成了"像运维一样复杂"。
