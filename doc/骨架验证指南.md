## 1. 这个包现在能做什么

v0.2.0 是第一个可用版本，管理对象是 **SQLite 实例**——它是唯一不需要下载引擎、装完即可用的引擎，因此适合作为第一个版本。

能力闭环：建库 → 浏览表结构 → SQL 读写 → 快照备份 → 恢复 → 删除（进回收站），全过程写审计。

平台自检仍然保留，作为安装后第一件事的"体检"：呈现 `TRIM_*` 变量、目录软链、真实落盘路径，并主动尝试越权写入（`/etc`、其他应用目录、`docker.sock`）验证权限边界。

## 2. 技术形态：Go 单二进制 + Vue3 内嵌前端

骨架早期用过 shell + CGI 的临时形态，仅为了在没有 Go 工具链时先把平台变量测出来。现在已换成正稿形态，**不会再退回 CGI**：

| 层 | 现状 | 说明 |
| --- | --- | --- |
| 后端 | Go 1.24，唯一第三方依赖 `modernc.org/sqlite` | 纯 Go 实现的 SQLite，`CGO_ENABLED=0` 可交叉编译；HTTP 用标准库 method 路由，不引框架 |
| 接入 | Unix Socket（`${TRIM_APPDEST}/app.sock`）+ 统一网关 `/app/niudbm` | 不声明 `service_port`，不占宿主端口 |
| 前端 | Vue 3 + TypeScript + Vite，产物 `//go:embed` 进二进制 | 无 UI 组件库，CSS 变量 + `prefers-color-scheme` 自带深浅色 |
| 元数据 | SQLite（`${TRIM_PKGVAR}/niudbm.db`） | 台账：实例、备份记录、审计、设置，迁移脚本幂等 |
| 实例数据 | `${TRIM_PKGVAR}/instances/<ULID>/data.db` | 文件名用 ULID，用户名只用于展示，从不参与拼路径 |
| 备份 | 优先共享目录 `/vol…/niudbm/backups/<ULID>/` | 共享目录不可写时自动回退私有 `var/backups`，不让服务起不来 |
| 启停 | 真实服务进程 | `cmd/main` 拉起二进制、等 socket 就绪、SIGTERM 优雅退出 |

三条与网关有关的设计，值得在真机验证时特别关注：

- **入口声明必须包在 `.url` 里**：`app/ui/config` 的顶层是 `{".url": {入口名: {...}}}`，入口名要与 manifest 的 `desktop_applaunchname` 完全一致。少一层 `.url` 时 `fnpack` 直接报 `cannot unmarshal string into Go value of type map[string]trimpack.UiApp`。
- **`<base href>` 由服务端注入**：页面可能被访问成 `/app/niudbm`（无尾斜杠），只靠相对路径会把静态资源解析到错误位置，所以 index 的 `<head>` 里由后端写入 `base="/app/niudbm/"`。
- **前缀双兼容**：网关是否剥离 `gatewayPrefix`，服务端在入口统一做一次归一化——带前缀就剔掉、不带前缀就原样，`/api/v1/health` 与 `/app/niudbm/api/v1/health` 都能命中。

## 3. 仓库结构

```
niudbm/                      打包目录，与最终版一致
├── manifest                 不声明 service_port；platform 由构建脚本按架构写入
│                            desktop_applaunchname 指向 ui/config 的入口名
├── config/
│   ├── privilege            run-as=package，包用户 niudbm，不加任何特权组
│   └── resource             data-share: niudbm/backups、niudbm/exports
├── cmd/                     9 个生命周期脚本（bash）
│   ├── install_init         前置检查：架构、内存、目标分区空间
│   ├── install_callback     建目录、把属主交给应用用户、写默认配置
│   ├── main                 start / stop / status（status 退出码 0 运行、3 停止）
│   ├── upgrade_init / upgrade_callback   升级前备份元数据库，保留最近 3 份
│   ├── uninstall_init / uninstall_callback   仅清缓存，用户数据全部保留
│   └── config_init / config_callback         授权目录变更
├── app/
│   └── ui/
│       ├── config           入口声明：{".url": {"niudbm.main": {…}}}
│       └── images/          64 / 256 图标
├── ICON.PNG                  64×64
├── ICON_256.PNG              256×256
└── wizard/                   预留（当前为空，格式待真机确认）

server/                       Go 服务端
├── cmd/niudbm/main.go        --socket / --addr / --prefix / --diag / --version
└── internal/
    ├── httpapi/              路由、静态资源、base 注入、身份 Header 判定、实例级互斥
    ├── engine/               SQLite 读写、SQL 护栏、VACUUM INTO 备份、原子恢复
    ├── store/                元数据库与迁移（实例/备份/审计/设置）
    ├── ulid/                 26 位 ULID（时间有序，单毫秒内单调）
    ├── diag/                 22 项自检（7 组），全部来自真实系统调用
    ├── platform/             TRIM_* 读取与开发模式回退
    └── webui/                //go:embed all:dist

web/                          Vue3 + TS + Vite 工程
└── src/                      api.ts（契约包解析）、views/、components/

scripts/
├── build.sh                  八阶段构建（检查 → 前端 → 测试 → 编译 → 组装 → 冒烟 → 打包 → 校验）
├── smoke.sh                  在容器里真跑一遍打包产物
├── smoke-in-container.sh     冒烟的具体步骤（建库→读写→备份→恢复→删除）
└── check-ui-config.py        校验入口声明与 manifest 一致

design/icon.svg               图标源文件
```

`server/internal/webui/dist` 是前端构建产物，**有意入库**：没有 Node 环境的机器也能直接编译出二进制。

## 4. 构建与打包

```bash
./scripts/build.sh                 # 默认双架构（amd64 + arm64），含测试与冒烟
./scripts/build.sh --pack          # 追加 fnpack 打包，产出两个 fpk
./scripts/build.sh --arch amd64    # 只出一个架构（排查问题用）
./scripts/build.sh --skip-web      # 前端产物已就绪，跳过 pnpm
./scripts/build.sh --skip-test     # 跳过测试与冒烟（禁止用于发布）
```

**默认就是双架构**：发布必须成对出包，避免漏包。八个阶段：

1. **静态检查**：9 个 cmd 脚本语法、3 个 JSON、manifest 必填字段、图标、可执行位、入口声明一致性；
2. **前端构建**：`pnpm install && pnpm build`，产物直接输出到 `server/internal/webui/dist`；
3. **后端测试**：`go vet` + `go test ./...`（引擎、台账、ULID、HTTP 端到端），失败即中止，不出包；
4. **Go 交叉编译**：`CGO_ENABLED=0 GOOS=linux`，`-trimpath -buildvcs=false`，版本从 manifest 读出注入 `-ldflags`；
5. **组装**：`.build/pkg-{arch}/` 复制 config、cmd、wizard、app/ui，放入二进制，再按架构重写 `manifest` 的 `platform`（amd64→x86、arm64→arm）；
6. **冒烟测试**：把刚编出来的二进制放进干净容器真跑一遍——启动、建库、SQL 读写、结构、备份、恢复、前端资源、审计、删除；本机跑不了该架构（镜像或模拟层缺失）时跳过而不失败；
7. **打包**：`fnpack build`，产出 `dist/niudbm-{version}-{arch}.fpk` 与 SHA256SUMS；
8. **产物校验**：二进制体积、`file` 架构匹配、静态链接、包内 manifest 与可执行位。

`build.sh` 会主动拦截五类常见错误：

- 声明了 `service_port`（纯网关应用不应声明）；
- 源文件 `platform=all` 却包含了架构相关二进制；
- manifest 缺必填字段，或 `desktop_applaunchname` 与 `app/ui/config` 的入口不一致；
- 入口声明缺 `gatewayPrefix` / `gatewaySocket`，或 `gatewaySocket` 写成了路径；
- 脚本忘记 `chmod +x`（最容易忽略、装上去才报错的坑）。

本机没有 Go 时，脚本自动改用 Docker 镜像（`GO_IMAGE` 可覆盖，默认 `golang:1.24`；`GO_PROXY` 默认 `goproxy.cn`）。`fnpack` 会先在 `PATH` 里找，找不到再试 `~/bin/fnpack`。

## 5. 三层验证手段

| 层次 | 手段 | 覆盖什么 | 命令 |
| --- | --- | --- | --- |
| 单元与端到端 | `go test ./...` | SQL 护栏（多语句/黑名单/字符串内关键字）、备份恢复往返、损坏备份拒绝、台账 CRUD、权限判定、完整实例生命周期 | `scripts/build.sh` 第 3 阶段 |
| 产物冒烟 | `scripts/smoke.sh <二进制> <arch>` | 打包出来的那个二进制真的能启动、embed 前端在、SQLite 能读写、恢复后数据回到备份时刻 | `scripts/build.sh` 第 6 阶段 |
| 平台自检 | `niudbm --diag` | 目录映射、权限边界、运行身份、架构与 C 运行库 | 安装后自动生成，也能 SSH 手工跑 |

**界面看结果**：应用中心 → 牛库管家 → 打开，概览页 + 自检页。

**SSH 看结果**：

```bash
/var/apps/niudbm/target/niudbm --diag          # 平台自检
tail -n 100 /var/apps/niudbm/var/logs/server.log   # 服务日志
ls -l /var/apps/niudbm/target/app.sock         # socket 是否起来
```

## 6. 自检项 → 核对项映射

自检共 22 项，分 7 组（运行身份 / 目录与路径 / 权限边界 / 系统环境 / 网络与网关 / 生命周期 / 数据与残余）。每项都带核对清单编号，例如：

- `P-02` 目录映射：`TRIM_PKGVAR`、`TRIM_PKGETC`、`TRIM_PKGTMP`、`TRIM_APPDEST`、`TRIM_PKGHOME` 是否真的可读写；
- `P-03` 权限边界：`/etc` 是否意外可写、其他应用目录是否可达、`docker.sock` 是否暴露；
- `P-05` 运行身份：是否以包用户而非 root 运行，是否与 `TRIM_UID` 一致；
- `P-12` 共享目录：`TRIM_DATA_SHARE_PATHS` 是否收到，备份能否落到共享目录；
- `P-17 / P-18` 架构与 C 运行库；
- `P-21` 服务是否真的活着（心跳文件）。

## 7. 这个包**不能**验证的项

- 应用商店上架审核链路（需要开发者账号走正式流程）
- 多用户并发下的会话隔离（单机家用场景暂不设计）
- fpk 签名校验（本地构建出的包未签名，真机安装需要允许第三方来源）
- 其他引擎的下载、校验、进程托管（v0.2.0 不含）
- 定时备份与任务中心（v0.2.0 不含）

## 8. 仍待真机确认的点

| 项 | 现状 | 想确认什么 |
| --- | --- | --- |
| `app/ui/config` 的 `icon` | 用官方模板的 `images/icon_{0}.png` | 平台是否会把 `{0}` 替换成 64/256 |
| `allUsers: true` | 所有用户可见入口 | 普通用户进入后能否正常看到只读界面 |

| 安装脚本属主 | `install_callback` 与 `main start` 都做了一次 `chown` 兜底 | 是否重复、是否与平台行为冲突 |
| `os_min_version` | 填 `1.1.3100` | 目标机器版本是否满足 |
| 网关是否剥离前缀 | 服务端双兼容 | 实际转发时的路径形态（决定后续能否精简） |

## 9. 本地开发

```bash
# 终端一：后端（开发模式自动走 TCP 8780，身份放行并按管理员处理）
cd server && go run ./cmd/niudbm --addr 127.0.0.1:8780

# 终端二：前端（Vite 热更新，/api 代理到 8780）
cd web && pnpm dev
```

开发模式下目录回退到 `$TMPDIR/niudbm-dev`，不会碰真机数据。`--diag` 同样可用。

跑测试：

```bash
cd server && go vet ./... && go test ./...
```

## 10. 下一步

v0.2.0 真机测试通过后，按这个顺序推进：

1. 导入已有 `.db` 文件（用户迁移已有数据库的刚需）
2. 定时备份与保留策略（按天/周，保留 N 份）
3. MySQL / PostgreSQL 引擎下载、校验、进程托管（需要授权校验与端口池）
4. 成员与权限（`instances` 的归属、只读成员）
5. 回收站可视化与清空策略
