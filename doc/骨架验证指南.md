# 牛库管家（NiuDBM）骨架验证指南

> 配套文档：[权限与平台核对清单](./权限与平台核对清单.md) ｜ [产品与技术方案](./牛库管家-NiuDBM-产品与技术方案.md) ｜ [数据模型与接口契约](./数据模型与接口契约.md)
>
> 对应版本：`niudbm 0.1.0`（自检包，**不含数据库功能**）

---

## 1. 这个包是什么

一个能装进 fnOS、能在应用中心里打开的**最小应用**，唯一用途是把核对清单里"只能靠真机行为兑现"的假设一条条测掉。

它不做数据库管理，只做三件事：

1. 安装后把平台注入的 `TRIM_*` 变量、目录软链、真实落盘路径呈现出来；
2. 主动尝试越权写入（`/etc`、其他应用目录、`docker.sock`），验证权限边界是否真的生效；
3. 提供 `start / stop / status`，验证平台对生命周期与退出码的调用语义。

---

## 2. 技术形态：Go 单二进制 + Vue3 内嵌前端

骨架早期用过 shell + CGI 的临时形态，仅为了在没有 Go 工具链时能先把平台变量测出来。现在已换成正稿形态，**不会再退回 CGI**：

| 层 | 现状 | 说明 |
| --- | --- | --- |
| 后端 | Go 1.22+，**纯标准库零第三方依赖** | 编译成单个静态二进制，无运行时依赖；`net/http` 的 method 路由（`GET /api/v1/health`），不引 Gin/Fiber |
| 接入 | Unix Socket（`${TRIM_APPDEST}/app.sock`）+ 统一网关 `/app/niudbm` | 不声明 `service_port`，不占宿主端口 |
| 前端 | Vue 3 + TypeScript + Vite，产物 `//go:embed` 进二进制 | 无 UI 组件库，CSS 变量 + `prefers-color-scheme` 自带深浅色 |
| 元数据 | 暂无 | 骨架还没有需要持久化的状态，SQLite 留到业务阶段 |
| 启停 | 真实服务进程 | `cmd/main` 拉起二进制、等 socket 就绪、SIGTERM 优雅退出 |

两条与网关有关的设计，值得在真机验证时特别关注：

- **`<base href>` 由服务端注入**：页面可能被访问成 `/app/niudbm`（无尾斜杠），只靠相对路径会把静态资源解析到错误位置，所以 index 的 `<head>` 里由后端写入 `base="/app/niudbm/"`。
- **前缀双兼容**：网关是否剥离 `gatewayPrefix` 尚未真机确认（P-08），服务端在入口统一做一次归一化——带前缀就剔掉、不带前缀就原样，`/api/v1/health` 与 `/app/niudbm/api/v1/health` 都能命中。

## 3. 仓库结构

```
niudbm/                      打包目录，与最终版一致
├── manifest                 不声明 service_port；platform 由构建脚本按架构写入
├── config/
│   ├── privilege            run-as=package，包用户 niudbm，不加任何特权组
│   └── resource             data-share: niudbm/backups、niudbm/exports
├── cmd/                     9 个生命周期脚本（bash）
│   ├── install_init         前置检查：架构、内存、目标分区空间
│   ├── install_callback     初始化目录、写默认配置、落安装标记
│   ├── main                 start / stop / status（status 退出码 0 运行、3 停止）
│   ├── upgrade_init / upgrade_callback
│   ├── uninstall_init / uninstall_callback   仅清缓存，用户数据全部保留
│   └── config_init / config_callback         授权目录变更
├── app/
│   └── ui/
│       ├── config           入口声明：gatewayPrefix + gatewaySocket
│       └── images/          64 / 256 图标
├── ICON.PNG                  64×64
├── ICON_256.PNG              256×256
└── wizard/                   预留（当前为空，格式待真机确认）

server/                       Go 服务端
├── cmd/niudbm/main.go        --socket / --addr / --prefix / --diag / --version
└── internal/
    ├── httpapi/              路由、静态资源、base 注入、身份 Header 判定
    ├── diag/                 22 项自检（7 组），全部来自真实系统调用
    ├── platform/             TRIM_* 读取与开发模式回退
    └── webui/               //go:embed all:dist

web/                          Vue3 + TS + Vite 工程
└── src/                      api.ts（base 推导）、useDiag.ts、views/

scripts/build.sh              静态检查 → 前端 → 交叉编译 → 组装 → 打包
design/icon.svg               图标源文件
```

`server/internal/webui/dist` 是前端构建产物，**有意入库**：没有 Node 环境的机器也能直接编译出二进制。

## 4. 构建与打包

```bash
./scripts/build.sh                 # 默认 amd64
./scripts/build.sh --arch arm64    # arm 包
./scripts/build.sh --arch all      # 双架构
./scripts/build.sh --skip-web      # 前端产物已就绪，跳过 pnpm
./scripts/build.sh --pack          # 追加 fnpack 打包
```

五个阶段：

1. **静态检查**：9 个 cmd 脚本语法、3 个 JSON、manifest 必填字段、图标、9 个可执行位；
2. **前端构建**：`pnpm install && pnpm build`，产物直接输出到 `server/internal/webui/dist`；
3. **Go 交叉编译**：`CGO_ENABLED=0 GOOS=linux`，`-trimpath -buildvcs=false`，版本从 manifest 读出注入 `-ldflags`；
4. **组装**：`.build/pkg-{arch}/` 复制 config、cmd、wizard、app/ui，放入二进制，再按架构重写 `manifest` 的 `platform`（amd64→x86、arm64→arm）；
5. **打包**：可选 `fnpack build`，产出 `dist/niudbm-{version}-{arch}.fpk` 与 SHA256SUMS。

`build.sh` 会主动拦截四类常见错误：

- 声明了 `service_port`（纯网关应用不应声明）；
- 源文件 `platform=all` 却包含了架构相关二进制；
- manifest 缺必填字段；
- 脚本忘记 `chmod +x`（最容易忽略、装上去才报错的坑）。

本机没有 Go 时，脚本自动改用 Docker 镜像编译（`GO_IMAGE` 可覆盖，默认 `golang:1.24`）。`fnpack` 仍需从飞牛开发者中心获取，本机未安装。

## 5. 怎么看结果

**路径一：应用中心 → 牛库管家 → 打开**，直接看到自检页（概览 + 诊断两页）。

**路径二：SSH 到 NAS 手工执行**

```bash
/var/apps/niudbm/target/niudbm --diag
```

**路径三：看接口返回**

```bash
curl -s --unix-socket /var/apps/niudbm/target/app.sock \
  http://localhost/app/niudbm/api/v1/diag
```

三种方式内容一致，都按 `通过 / 需确认 / 未通过` 三态输出。**未通过项必须处理完再进入下一阶段。**

服务运行日志在 `var/logs/server.log`，同步记录每条请求的路径、状态码与耗时。

## 6. 自检项 → 核对项映射

共 7 组 22 项（开发模式下条目数量会因缺少 `TRIM_*` 略有增减）。

| 分组 | 自检项 | 对应核对项 | 通过意味着什么 |
| --- | --- | --- | --- |
| 运行身份 | 运行身份 | P-05 | 进程不是 root，最小权限前提成立 |
| 运行身份 | 身份与声明一致 | P-05、P-07 | `TRIM_UID` 与实际 uid 一致，拿到的身份可信 |
| 目录与路径 | 数据/配置/临时/安装/用户目录 | P-02 | `target/etc/var/tmp/home` 软链与变量一一对应且可写 |
| 目录与路径 | 共享目录 | P-12、P-13 | `data-share` 已创建、路径变量正确、应用用户可写 |
| 权限边界 | 写入 `/etc` | P-03、P-05 | 系统目录越权被拒绝 |
| 权限边界 | 写入其他应用目录 | P-03、P-16 | 应用间隔离有效 |
| 权限边界 | 访问 Docker Socket | P-03、P-06 | 未获得 Docker 控制权（原生方案的关键前提） |
| 权限边界 | 用户授权目录 | P-16 | 已收到授权路径，导入导出可直连共享目录 |
| 系统环境 | CPU 架构 | P-17 | 当前架构与系统声明一致 |
| 系统环境 | 操作系统 / 硬件资源 | — | 记录基线，供引擎选型参考 |
| 系统环境 | C 运行库 | P-18 | 记录 glibc 版本，作为引擎分发基线 |
| 端口与网络 | 端口池 | P-19 | 33000–33004 可绑定（**不含对外可达性**） |
| 端口与网络 | 对外暴露 | P-19 | 永远为"需确认"，须在真机用局域网设备实测 |
| 平台集成 | 平台变量注入 | P-02、P-07 | 变量集合与文档一致 |
| 平台集成 | `TRIM_API_TOKEN` | P-15 | 令牌已注入（内容不打印） |
| 生命周期 | 安装标记 / 服务心跳 | P-20、P-21 | 生命周期脚本被正确调用、服务确实活着 |

设计原则：每条结论都来自一次真实系统调用（建目录、写临时文件、绑端口、读权限位），**不做"看起来正常"的推断**。Docker Socket 只按权限位判断，绝不打开文件，避免影响宿主机上的容器服务。

## 7. 这个包**不能**验证的项

必须诚实列出，避免误判"装上了就等于方案成立"：

| 核对项 | 为什么测不了 | 怎么补 |
| --- | --- | --- |
| P-01 安装位置可选 | 需要装两次（系统盘 / 数据卷）对比 | 真机各装一次，记录落盘路径 |
| P-04 升级保留数据 | 需要两个版本才能升 | 发 0.1.1 后从 0.1.0 升级验证 |
| P-08 网关是否剥离前缀 | 本机没有网关，只能保证两种转发都兼容 | 真机上看 `server.log` 里记录的原始路径 |
| P-09 / P-10 Header 与 WebSocket | 无网关注入，Header 只能手工造 | 真机打开页面看概览页的身份字段 |
| P-11 远程访问 | 需要 FN Connect / 反代环境 | 真机远程各走一遍 |
| P-14 文件选择器 | `micro_app=false`，未引入 JS SDK | 需要开 `micro_app` 并接 SDK |
| P-23 断电恢复 | 需要真实断电 | 真机做 kill -9 与断电各一次 |
| P-24 / P-25 上架合规 | 需完整上架走一遍 | 提交前人工复核三个配置文件 |

## 8. 骨架里故意留的待确认点

| 项 | 现状 | 待确认内容 |
| --- | --- | --- |
| `desktop_applaunchname` | **未声明** | 该字段指向可执行的启动程序，是否要填 `app/niudbm` 需真机确认；目前只有 `desktop_uidir` |
| `app/ui/config` 的 url | 走 `gatewayPrefix` + `gatewaySocket` | 是否还需要 `port` 字段；`gatewayPrefix` 是否要尾斜杠 |
| `wizard/` | 空目录 | `fnpack` 是否强制要求安装向导；若不强制则保持为空直到需要"选择安装位置" |
| `os_min_version=1.1.3100` | 按网关最低版本填写 | 是否可下调，取决于网关功能引入的系统版本 |
| `platform` | 源文件写 `x86`，构建时按架构重写 | `fnpack` 是否接受一份源码出两个包，还是必须各自改 manifest |
| 网关前缀 | 服务端做双兼容 | 若网关确认会剥离前缀，可去掉兼容分支让代码更直白 |

## 9. 本地开发

```bash
# 终端一：后端（开发模式自动走 TCP 8780、目录回退到临时目录）
cd server && go run ./cmd/niudbm --addr 127.0.0.1:8780 --prefix ""

# 终端二：前端（Vite 热更新，/api 代理到 8780）
cd web && pnpm dev
```

没有 `TRIM_*` 变量时，`platform.Load` 会把 `target/etc/var/tmp/home` 全部指向临时目录，运行身份的"平台声明一致"一项自动转为"需确认"，不会误报成失败。

## 10. 下一步

1. 安装 `fnpack`，执行 `./scripts/build.sh --arch all --pack` 出双架构包；
2. 在 D1（x86）装上，打开页面把 `未通过` 项逐条处理；
3. 在 D2（arm）重复一次，重点看 P-17、P-18；
4. 真机确认 P-08 前缀行为后，再决定是否简化兼容代码，随后进入引擎接入阶段。

**不要跳过第 2 步直接写业务代码**——目录与权限若与预期不符，业务代码里的路径假设会全部作废。
