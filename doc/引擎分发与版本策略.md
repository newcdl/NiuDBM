# 牛库管家（NiuDBM）引擎分发与版本策略

> 配套文档：[产品与技术方案](./牛库管家-NiuDBM-产品与技术方案.md) ｜ [权限与平台核对清单](./权限与平台核对清单.md)
>
> 版本：v1.0 ｜ 定位：决定"装完就能用"与"安装包有多大"之间的平衡
>
> 所有体积为量级估算，实际以构建产物为准；许可判断非法律意见，发布前需法务确认。

---

## 0. 结论摘要

| 决策 | 结论 |
| --- | --- |
| 是否随包内置全部引擎 | **否**。双架构全内置会让安装包膨胀到数百 MB，与"轻量"定位冲突 |
| 内置哪些 | 仅 `SQLite`（编译进主程序）与 `Valkey`（单二进制，约 10 MB 级） |
| 按需下载哪些 | `MariaDB`、`MySQL`、`PostgreSQL`（首次创建实例时下载对应架构包） |
| 无法下载时 | 支持**离线导入**本地引擎包；UI 明确标注"当前离线可用"状态 |
| MongoDB | **不自建分发**，只做纳管（许可与体积双重原因） |
| 版本线 | 每引擎同时维护 2 条稳定线，大小版本并存，小版本可自动跟随 |
| 兼容基线 | 用**低 glibc 基线**构建，向上兼容；禁止 `-march=native` / `x86-64-v3` |
| 校验 | SHA-256 + 独立签名，缺一不放行；下载源可替换但校验不可绕过 |

## 1. 三种分发形态

### 1.1 形态定义

| 形态 | 机制 | 首启体验 | 包体成本 | 适用 |
| --- | --- | --- | --- | --- |
| **A 内置** | 随 fpk 打包，安装即存在 | 装完立刻可建库 | 直接计入安装包 | 极小引擎、无外部依赖 |
| **B 按需** | 首次创建该引擎实例时下载对应架构包 | 需一次联网下载（有进度与体积提示） | 几乎为零 | 中大引擎 |
| **C 纳管** | 不部署引擎，只接管已有实例 | 立刻可用（用户已有库） | 零 | 许可受限或体积极大的引擎 |

### 1.2 决策规则

按顺序判定，命中即停：

1. 许可不允许自由分发 → **C 纳管**
2. 解压后体积 < 20 MB 且无动态库依赖 → **A 内置**
3. 其他 → **B 按需**，且必须同时提供离线导入通道

### 1.3 为什么不"全都内置"

按双架构（x86_64 + arm64）估算：MariaDB 约 80 MB、PostgreSQL 约 40 MB、Valkey 约 10 MB、MongoDB 约 150 MB（压缩态量级），合计已接近 300 MB，解压后接近 1 GB。这会带来三个连锁问题：

- 系统分区小的设备安装失败或写满；
- 每次发版都要重新分发全部引擎，升级包巨大；
- 引擎补丁版本被迫与 App 版本绑定，安全修复滞后。

**所以：内置只换取"零等待"的极小引擎，其余用"按需 + 离线导入"换取体积与更新灵活性。**

## 2. 引擎清单与许可边界

| 引擎 | 计划版本线 | 许可 | 可自由分发 | 默认形态 | 说明 |
| --- | --- | --- | --- | --- | --- |
| SQLite | 3.4x | Public Domain | 是 | A 内置 | 编译进主程序，不独立分发 |
| Valkey | 8.x | BSD-3-Clause | 是 | A 内置 | Redis 的宽松许可分支，作为默认键值引擎 |
| Redis | 7.2.x | BSD-3-Clause（旧版） | 是 | B 可选 | 仅保留旧线以兼容存量用户习惯 |
| MariaDB | 10.11 LTS / 11.4 LTS | GPLv2 | 是（需履行 GPL 义务） | B 按需 | P0 主力关系型引擎 |
| MySQL | 8.0 / 8.4 LTS | GPLv2 | 是（需履行 GPL 义务） | B 按需 | 与 MariaDB 二选一，避免重复占用磁盘 |
| PostgreSQL | 16 / 17 | PostgreSQL License | 是 | B 按需 | 需自行构建产物（官方无通用 Linux 二进制） |
| MongoDB | — | SSPL | **否**（非 OSI 许可） | C 纳管 | 不随包、不代下载，只接管用户已有实例 |

### 2.1 许可要点（发布前必须过一遍）

- **GPLv2 引擎（MariaDB / MySQL）**：随包或代为分发时需履行相应义务（附许可证文本、提供对应源码获取方式）。按需下载由用户发起，仍需在引擎包与"关于"页面提供源码出处与许可证。
- **Redis 许可变更**：7.4 起转为 RSALv2 / SSPLv1，8.0 增加 AGPLv3 选项。因此**默认键值引擎改用 Valkey（BSD-3）**，Redis 仅保留 7.2.x 旧线，避免把许可风险带进产品。
- **MongoDB 的 SSPL 不是 OSI 认可的开源许可**，代分发风险高，这也是把 MongoDB 降级为"纳管"的关键原因，不只是体积问题。
- 所有引擎包的"关于"页面统一展示：引擎名、版本、许可证、源码地址、本地包校验值。

> 结论：**许可边界直接决定了形态选择，不是事后补丁。**

## 3. 体积与资源预算

| 引擎 | 压缩包（单架构） | 解压后 | 常驻内存（低配档） | 备注 |
| --- | --- | --- | --- | --- |
| SQLite | — | 计入主程序（约 1–2 MB） | ≈ 0 | 进程内 |
| Valkey | 约 3–6 MB | 约 10–15 MB | 约 5–15 MB | 单二进制 |
| MariaDB | 约 60–90 MB | 约 250–400 MB | 约 80–150 MB | 含服务端与备份工具 |
| MySQL | 约 50–80 MB | 约 300–450 MB | 约 120–200 MB | 与 MariaDB 互斥安装 |
| PostgreSQL | 约 25–40 MB | 约 80–120 MB | 约 50–100 MB | 需自建产物 |
| MongoDB | —（不分发） | — | — | 纳管不占本地磁盘 |

**磁盘水位规则**：创建实例前要求目标卷剩余空间 ≥ 引擎解压体积 × 2 + 实例初始数据 1 GB；低于阈值时禁止新建并给出具体数字，而不是笼统提示"空间不足"。

## 4. 引擎包规范（Engine Bundle）

### 4.1 包结构

```
{engine}-{version}-{arch}/
├── meta.json          # 元数据与兼容声明
├── bin/               # 可执行文件
├── lib/               # 私有动态库（如有）
├── share/             # 初始化 SQL、字符集、时区数据
├── licenses/          # 许可证文本与源码出处
└── checksums.txt      # 包内文件校验清单
```

### 4.2 元数据字段

| 字段 | 用途 |
| --- | --- |
| `id` / `engine` / `version` / `arch` | 唯一标识与匹配 |
| `glibc_min` | 运行所需最低 glibc，启动前比对，不满足直接拒绝并给可读原因 |
| `cpu_baseline` | 指令集基线（x86-64-v1 / armv8-a），用于老旧 CPU 兜底判断 |
| `size_packed` / `size_unpacked` | 下载前展示体积，解压前校验磁盘 |
| `sha256` | 整包校验 |
| `signature` | 发布方签名，防止镜像源被篡改 |
| `entrypoints` | 服务端二进制、备份工具、健康检查命令 |
| `default_profiles` | 低配/标准/性能三档参数模板 |
| `capabilities` | 支持的备份方式、是否支持在线一致性快照 |
| `eol_date` | 生命周期终止日，用于提前提示用户升级 |

### 4.3 校验与放行规则

1. 下载完成先校验 `sha256`，再验签；
2. 两者任一失败即删除临时文件并报错，**不允许"跳过校验继续安装"**；
3. 解压后按 `checksums.txt` 做一次文件级校验；
4. 首次启动前做 `glibc_min` 与 `cpu_baseline` 预检，任一不满足则拒绝启动并给出可执行建议（改用其他版本/改为纳管）。

## 5. 目录布局与多版本共存

```
var/
├── engines/
│   └── {engine}/{version}/{arch}/     # 解压后的引擎运行时（只读）
├── instances/
│   └── {instance-id}/
│       ├── data/                      # 引擎数据（0700）
│       ├── etc/                       # 实例配置（0600）
│       └── runtime.json               # 指向所用引擎版本、端口、状态
├── cache/downloads/                   # 下载中/待校验（启动时清理残留）
└── logs/
etc/
├── engine-sources.json                # 下载源配置（0600）
└── trust/                             # 受信公钥
shares/niudbm/backups/                 # 用户可见的备份产物
```

- **多版本共存**：`engines/{engine}/{version}` 并列存放，实例通过 `runtime.json` 固定版本，互不影响。
- **升级不改路径**：升级只切换实例指向的版本号，不移动数据目录。
- **回收**：无实例引用的引擎版本在 7 天后提示可清理，不自动删除。

## 6. 分发链路

### 6.1 下载源优先级

1. **官方镜像源**（自建对象存储 / CDN，按区域就近）
2. **上游官方源**（作为备用，避免镜像故障导致不可用）
3. **用户自定义源**（企业内网、离线文件服务器）
4. **本地离线包导入**（无外网设备）

源配置可改，但**校验链不可关闭**——自定义源同样要过哈希与签名。

### 6.2 下载流程要点

- 先取元数据清单，展示"版本 + 体积 + 变更说明"再让用户确认；
- 流式下载 + 断点续传，中断不清空已下载分片；
- 单实例串行、多实例限并发（默认 2），避免把家庭带宽打满；
- 全程写任务日志，可在"任务中心"看到进度与失败原因。

### 6.3 失败处理与用户可见文案

| 场景 | 文案方向 | 必须提供的出口 |
| --- | --- | --- |
| 无法连接下载源 | "无法连接引擎下载源，可能是网络受限" | 重试 / 更换源 / 离线导入 |
| 校验失败 | "引擎包校验不通过，已丢弃" | 重试 / 更换源（不提供跳过） |
| 磁盘不足 | "需要 1.2 GB，当前可用 600 MB" | 清理建议 / 换卷 |
| glibc 不满足 | "当前系统库版本过低，该引擎版本无法运行" | 推荐兼容版本 / 改为纳管 |

**原则**：任何失败都要给"下一步能点什么"，不能只报错。

### 6.4 离线导入

- 支持导入单个引擎包文件，导入时执行同一套校验；
- 导入后标记为"本地包"，在引擎列表中显示来源与有效期；
- 面向内网/无外网设备，需在文档中给出包命名规则，便于批量分发。

## 7. 引擎级安装、升级与回滚

### 7.1 新建实例

元数据确认 → 磁盘水位检查 → 引擎包就位（已有则跳过）→ 架构与 glibc 预检 → 端口分配 → 目录初始化 → 生成初始凭据（入保险箱）→ 启动 → 健康检查 → 写入台账与审计。

### 7.2 版本升级策略

| 类型 | 策略 | 用户感知 |
| --- | --- | --- |
| 补丁版本（如 10.11.9 → 10.11.10） | 可在维护窗口内自动跟随，默认需用户确认 | 一条通知 + 一键执行 |
| 次版本（同大版本线内） | 需用户选择，升级前自动备份 | 预检报告 + 确认 |
| 大版本（如 10.11 → 11.4） | **必须手动**，强提示不可逆风险，要求先完整备份 | 独立流程 + 二次确认 |

### 7.3 回滚与不可逆边界

| 场景 | 可回滚性 | 处理 |
| --- | --- | --- |
| 引擎二进制切换失败（数据未迁移） | 可回滚 | 切回旧版本指针并重启 |
| 补丁/次版本升级 | 通常可回滚 | 保留旧运行时不删，回滚时切指针 |
| MySQL / MariaDB 大版本升级 | **可能不可逆**（数据字典变更） | 只允许"备份 → 升级 → 验证"，回滚靠恢复备份 |
| PostgreSQL 大版本升级 | **不可逆**（需 `pg_upgrade`） | 同上，且必须提示耗时与所需磁盘 |
| 用户手动改过引擎参数导致启动失败 | 可回滚 | 恢复到升级前参数快照 |

**硬规则**：任何提示"不可逆"的操作，必须在执行前自动生成一份完整备份，且备份完成才允许继续。

## 8. 架构与构建

### 8.1 构建矩阵

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| CPU 架构 | x86_64 / arm64 | 分别产出独立 fpk（`platform` 分别为 `x86` / `arm`） |
| glibc 基线 | 取目标最低支持系统的 glibc 版本 | 低基线构建，向上兼容，避免"新系统能跑、老系统跑不了" |
| 指令集基线 | x86-64-v1 / armv8-a | **禁止** `-march=native`、`x86-64-v3`，否则老 CPU 直接非法指令 |
| 优化 | `-O2` + 去除调试符号 | 兼顾体积与性能 |

### 8.2 glibc 兼容策略

1. 在较低基线环境中编译（容器化构建环境固定版本），而不是在开发机上直接编译；
2. 构建后扫描二进制的符号版本需求（`GLIBC_2.x`），写入 `meta.json` 的 `glibc_min`；
3. 运行时预检 + 三元兜底：**推荐兼容版本 → 建议纳管 → 明确不支持**。

这是"引擎能在多数飞牛设备上跑起来"的关键工程约束，也是核对清单 P-17 / P-18 的直接来源。

## 9. 每实例默认资源档位

| 引擎 | 低配（≤8 GB 内存设备） | 标准（16 GB） | 说明 |
| --- | --- | --- | --- |
| MariaDB | buffer pool 128 MB，连接 50 | 512 MB，连接 100 | 缓冲池是内存大户，按设备内存推荐 |
| PostgreSQL | shared_buffers 128 MB，连接 50 | 512 MB，连接 100 | 与 MariaDB 同量级 |
| Valkey | maxmemory 64 MB，LRU 淘汰 | 256 MB | 默认开启内存上限，避免吃光整机 |
| SQLite | 无（进程内） | 无 | 由主程序统一控制 |

**规则**：默认值必须是"低配安全档"，性能档需用户显式选择；实例数超过设备承载时给出降级建议而不是放任。

## 10. 风险与待验证

| 编号 | 风险 / 待验证 | 关联核对项 | 应对 |
| --- | --- | --- | --- |
| E-01 | 下载源在部分网络环境不可达 | 新增 | 多源 + 离线导入 + 明确文案 |
| E-02 | ARM 平台引擎二进制缺失或不可运行 | P-17、P-18 | 该引擎在该架构标"不支持"，引导纳管 |
| E-03 | 引擎许可义务未履行 | P-25 | 统一"关于"页 + 许可证随包 + 法务复核 |
| E-04 | 大版本升级后无法回滚 | P-22 | 强制备份 + 不可逆二次确认 |
| E-05 | 镜像源被篡改 | — | 签名 + 哈希双重校验，不允许跳过 |
| E-06 | 多实例并发下载打满带宽 | — | 并发限流 + 任务队列 |
| E-07 | 引擎包体积估算偏差导致体验落差 | — | 首版构建后回填真实体积到本文档 |

## 12. 一句话收口

引擎不是"塞进安装包就完事"的静态资源，而是一条**带许可约束、带架构约束、带校验链的分发链路**；这条链路的可靠性，直接决定用户第一次点"创建数据库"时是等 30 秒，还是看到一个看不懂的报错。
