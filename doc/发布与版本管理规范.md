## 0. 先分清三条版本轴

产品里有三个独立的版本号，混用会导致"引擎升个补丁却要发整包"这类错误。

| 版本轴 | 例子 | 谁决定 | 变化频率 | 变化后影响谁 |
| --- | --- | --- | --- | --- |
| **应用版本**（fpk） | `1.2.0` | 我们 | 按功能节奏 | 用户需在应用中心升级整个应用 |
| **引擎版本** | `MariaDB 11.4.5` | 上游 + 我们的分发 | 跟随上游补丁 | 只影响对应实例，**不需要发新版应用** |
| **元数据 schema** | `schema 7` | 我们的数据模型 | 随应用版本 | 升级时自动迁移，降级可能不支持 |

**核心规则**：引擎补丁通过"按需下载新版本"解决，不绑应用发版；schema 变更必须随应用版本发布，且需要迁移脚本。

## 1. 版本号规则

### 1.1 语义化版本与递增判定

采用 `MAJOR.MINOR.PATCH`，按**用户可感知的变化**判定，而不是按代码量：

| 变更内容 | 升哪一位 | 示例 |
| --- | --- | --- |
| 破坏性变更：接口不兼容、schema 不可降级、权限模型调整 | **MAJOR** | 1.4.0 → 2.0.0 |
| 新增能力：新引擎、新备份目标、新页面 | **MINOR** | 1.4.0 → 1.5.0 |
| 缺陷修复、文案调整、性能优化、引擎版本更新 | **PATCH** | 1.4.0 → 1.4.1 |

判定口诀：**用户要改使用习惯 → MAJOR；用户多了一个功能 → MINOR；用户什么都没变但更好用了 → PATCH。**

### 1.2 预发布与构建号

| 阶段 | 写法 | 用途 |
| --- | --- | --- |
| 内测 | `1.5.0-beta` | 功能完整但未验证，可能不带完整迁移 |
| 候选 | `1.5.0-rc` | 功能冻结，只修缺陷 |
| 正式 | `1.5.0` | 可发布 |

- 构建号**不写进版本号**，只记在构建产物元信息里（便于定位"同一个版本不同构建"）。
- 预发布版本不得进入 `main` 打正式 tag，只能作为测试包分发。

> **待验证**：`manifest.version` 对 `-beta` / `-rc` 后缀的接受程度。平台示例中出现过 `2.1.3-beta` 形式，但 `-beta.1` 这种带点号的后缀未确认。若不支持，统一降级为不带序号的 `-beta`。

### 1.3 版本号必须一致的位置

一次发布中，以下五处必须完全相同，任一不一致即视为发布失败：

1. `manifest` 的 `version`
2. 应用内「关于」页显示版本
3. 构建产物文件名
4. Git tag
5. `CHANGELOG.md` 顶部条目

## 2. 分支模型

### 2.1 当前模型

| 分支 | 角色 | 允许的操作 |
| --- | --- | --- |
| `main` | 发布线，永远对应"可发布状态" | 只接受来自 `dev` 的合并，以及发布后的 tag |
| `dev` | 开发线，日常所有改动 | 直接提交，允许中间态 |

### 2.2 合并时机

只在**准备发版时**合并，不做日常同步。合并方式固定为：

```
git checkout main
git merge --no-ff dev -m "release: v1.5.0"
git tag -a v1.5.0 -m "v1.5.0"
```

`--no-ff` 是硬要求：保留合并提交，才能从主干看清"哪些提交属于哪个版本"。

### 2.3 热修流程

发布后线上发现缺陷，**不直接在 `main` 上改**：

1. 在 `dev` 修复并提交；
2. 验证通过后合并到 `main`；
3. 版本号升 PATCH（如 `1.5.0` → `1.5.1`），重新打 tag；
4. 同步更新 `CHANGELOG.md`。

小团队不开 `hotfix/*` 分支，避免分支数量超过维护能力。

### 2.4 分支纪律

| 禁止项 | 原因 |
| --- | --- |
| 直接向 `main` 提交代码 | 破坏"main 永远可发布"的承诺 |
| 对已发布 tag 做 force push / 移动 tag | 已分发的版本无法召回，移动 tag 等于篡改历史 |
| 在 `dev` 上长期不提交（攒一大坨） | 出问题时无法定位、无法回滚到中间态 |
| 用 `git commit --amend` 修改已推送到远程的提交 | 同样属于改写历史 |

### 2.5 未来接入远程仓库后的规则

当前为纯本地仓库，接入远程（GitHub / 自建 Gitea）后追加：

- `main` 与 `dev` 均开启分支保护，禁止直推；
- 合并需通过一次自审（小团队不搞多人评审的形式主义，但要留一次"隔天再看"的记录）；
- tag 保护开启，禁止删除与移动。

## 3. 提交规范

### 3.1 结构

```
type: 一句话摘要（不超过 50 字，中文，动词开头）

- 要点一：做了什么、为什么
- 要点二：影响的模块或文档
- 要点三：验证方式（如"已核对 P-09"）
```

### 3.2 type 取值

| type | 用于 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat: 支持 PostgreSQL 实例纳管` |
| `fix` | 缺陷修复 | `fix: 修复恢复任务并发导致的状态错乱` |
| `docs` | 文档 | `docs: 补充引擎许可边界说明` |
| `refactor` | 重构（不改行为） | `refactor: 抽出引擎驱动接口` |
| `perf` | 性能 | `perf: 降低指标采样写入频率` |
| `test` | 测试 | `test: 补齐备份恢复的幂等用例` |
| `build` | 构建与打包 | `build: 双架构 fpk 构建脚本` |
| `chore` | 杂项 | `chore: 更新忽略规则` |

### 3.3 写法对照

| 差 | 好 | 原因 |
| --- | --- | --- |
| `update` | `fix: 修复端口池未释放导致无法新建实例` | 一眼看出改了什么 |
| `改了点东西` | `docs: 契约补充 adopted 实例字段约束` | 可检索 |
| `feat: 大量改动` | `feat: 新增离线引擎包导入` | 单一职责 |

**一个提交只做一件事**。文档与代码的改动如果属于同一件事，可以同提交；属于两件事，必须拆开。

### 3.4 与文档的关联

- 涉及方案变更 → 提交正文写清"更新了哪一节"；
- 关闭核对项 → 写"P-12 通过（x86，日期）"；
- 修复缺陷 → 关联触发条件与影响范围，方便后续回归。

## 4. 变更日志

### 4.1 两套日志，用途不同

| 日志 | 读者 | 位置 | 长度 |
| --- | --- | --- | --- |
| `CHANGELOG.md` | 用户 + 我们自己 | 仓库根目录 | 不限，按版本分区 |
| `manifest` 的 `changelog` | 只给用户，在应用中心升级弹窗里看 | 打包进 fpk | **3–5 条短句，每条 ≤ 30 字** |

### 4.2 分区

每个版本固定四段，**没有内容就删掉整段**，不留"无"：

```
## v1.5.0（2026-11-02）

### 新增
- 支持 PostgreSQL 16 实例创建

### 改进
- 创建向导的引擎选择改为按使用场景展示

### 修复
- 修复备份任务在机械盘上偶发超时

### 安全
- 显示密码操作全部记入审计
```

### 4.3 写法要求

| 要求 | 反例 | 正例 |
| --- | --- | --- |
| 面向用户 | `refactor driver layer` | `数据库列表加载更快` |
| 说结果不说过程 | `优化了 SQL 拼接方式` | `备份记录加载速度提升约 3 倍` |
| 破坏性变更置顶 | 藏在最后一条 | 段落最上方，标 `⚠` 并说明需要用户做什么 |
| 不写内部代号 | `修 PAN-231` | `修复删除实例后端口未释放的问题` |

## 5. 发布流程

### 5.1 发布前置条件（不满足则不得发版）

| 条件 | 判定标准 |
| --- | --- |
| 红线核对项通过 | P-05、P-16、P-19、P-22 全部为「通过」，且有证据 |
| 文档同步 | 方案 / 契约 / 核对清单与实现一致，无"待补"标记 |
| 双架构可用 | x86 与 arm 各完整安装一次并走完建库→备份→恢复 |
| 升级路径可用 | 上一正式版 → 本版本升级成功，且数据完整 |
| 卸载路径可用 | "保留数据"与"彻底删除"两条路径均验证 |
| 版本号一致 | §1.3 五处一致 |

### 5.2 步骤清单

1. `dev` 上完成功能与文档，自测通过；
2. 更新 `CHANGELOG.md` 与 `manifest.changelog`；
3. 提升 `manifest.version` 与关于页版本号；
4. 构建双架构产物，记录构建元信息；
5. 在干净设备安装验证（§5.1 全部条件）；
6. 合并到 `main`（`--no-ff` 保留记录）；
7. 打带注释 tag：`git tag -a v1.5.0 -m "v1.5.0"`；
8. 生成产物校验文件；
9. 按 §5.4 准备上架材料；
10. 回到 `dev` 继续开发（发版不影响开发线）。

### 5.3 产物命名与校验

```
niudbm-1.5.0-x86.fpk
niudbm-1.5.0-arm.fpk
niudbm-1.5.0-SHA256SUMS.txt
```

- 架构必须分开打包（`manifest.platform` 分别为 `x86` / `arm`），**不使用 `all`**，避免把不匹配的二进制装到用户设备上；
- 复用引擎包的校验逻辑：产物必须可被独立校验；
- 构建应尽量可复现：固定工具链版本，记录构建环境信息。

### 5.4 上架材料

| 材料 | 要求 |
| --- | --- |
| `.fpk` 包 | 双架构，`fnpack build` 无告警 |
| 应用图标 | 64 与 256 两种尺寸，圆角矩形主体，符合系统视觉 |
| 截图 | **真实界面**，覆盖：创建向导、实例详情、备份、任务中心；不使用占位图 |
| 应用描述 | 说明定位与核心能力，不堆砌技术词 |
| 更新说明 | 与 `manifest.changelog` 一致 |
| 权限说明 | 逐项解释 `api-scope` 与授权目录用途，便于审核 |
| 测试记录 | 覆盖的系统版本、机型、架构清单 |

### 5.5 阶段测试包（每个里程碑都出，不等功能全做完）

节奏固定在[路线图 §5](./牛库管家-MySQL单引擎-路线图.md)的 M0–M5：**每完成一个阶段就出一个小版本 fpk 交给真机**，不攒到最后一次发。理由：真机环境（飞牛 fnOS、Docker 权限、卷与目录、手机浏览器）里的问题越晚发现越贵，而阶段包能把问题钉在当时的改动范围内。

一个阶段包的最小动作：

```
[ ] 升 manifest.version（按路线图的小版本号，0.1.1 → 0.1.2 …）
[ ] 改 manifest.changelog 为 3–5 条用户能看懂的短句（上一版说明不累积）
[ ] 改 server/cmd/niudbm/main.go 的默认 version（与 manifest 前缀一致，带 -dev）
[ ] CHANGELOG.md 顶部加本版本条目
[ ] 写 doc/真机测试清单-v<版本>.md：P0 主线、本版修复项逐条验法、故意没做清单
[ ] scripts/build.sh --pack 出双架构 fpk + SHA256SUMS
[ ] 带 Docker 冒烟：SMOKE_DOCKER=1 scripts/smoke.sh dist/niudbm-linux-amd64 amd64
```

真机清单必须写清「这一版故意没做」的部分，否则测试者会把待做功能当缺陷报，来回确认的成本比写清单高。

阶段包可直接覆盖安装上一版（升级路径要测），不必先卸载。

## 6. 兼容与回滚

### 6.1 向后兼容承诺

由于应用升级由用户在应用中心手动触发，**不存在强制升级**。因此：

- 新版本必须能读取**上一个大版本**写入的数据（至少兼容一个 MAJOR）；
- 接口新增字段必须带默认值，旧前端不因缺字段崩溃；
- 需要用户手动处理的不兼容，必须在 `CHANGELOG` 顶部给出步骤，而不是静默失败。

### 6.2 schema 迁移与降级

| 情况 | 处理 |
| --- | --- |
| 升级前 | 自动备份元数据库，记录版本号 |
| 迁移中 | 迁移失败即回滚到备份并恢复旧二进制 |
| 升级后降级 | **默认不支持**；若用户强行降级，应用启动即拒绝运行并提示"数据已被高版本升级，请重装高版本" |
| 数据卷 | 迁移只改 `var/niudbm.db`，不触碰各实例数据目录 |

### 6.3 事故回滚路径

| 场景 | 动作 |
| --- | --- |
| 刚发布即发现严重缺陷 | 立即发布 PATCH 修复；不做 tag 回退（已分发版本无法召回） |
| 用户升级后异常 | 引导卸载"保留数据"→ 安装旧版 → 数据可读（前提：未跨 MAJOR） |
| 引擎版本问题 | 不涉及应用回滚，直接切回旧引擎版本即可 |

## 8. 风险

| 编号 | 风险 | 应对 |
| --- | --- | --- |
| R-01 | 预发布后缀格式不被平台接受 | 首版用最简形式（`-beta`），实测后固化写法 |
| R-02 | 版本号五处不一致导致用户困惑 | 用检查表强制核对；构建脚本从单一来源读取版本 |
| R-03 | 跨 MAJOR 升级后用户降级导致数据不可读 | 启动时校验 schema 版本，明确拒绝并给指引 |
| R-04 | 本地仓库无备份，磁盘损坏即丢失 | 定期推送到私有远程；至少保留一份异地副本 |
| R-05 | 发版时忘记同步文档，实现与设计脱节 | 发布检查表把"文档同步"设为前置条件 |
| R-06 | 只测了一种架构就发版 | 检查表强制双架构，且要求真机 |

---

## 9. 一句话收口

版本管理的价值不在于编号好看，而在于**任何一个线上问题都能顺着 tag 找回当时的代码、文档和决策**——所以 tag 不许动，历史不许改，版本号五处必须对得上。
